## 验证码识别逆向分析（当天第二轮，未完成）

用户要求「把验证码识别写好」。采了 60 张样本（`captcha_samples/`，间隔 1s），
做了完整的离线分析。**结论：模板匹配路线需要自建模板库，靠猜字体行不通。**

### 已确证的事实（可直接依赖）

| 事实 | 证据 |
|---|---|
| 图片为 **100×25 RGBA**，含 **130 种颜色** | `captcha_samples/0010.png` 实测 |
| 服务端**开了抗锯齿**，每字符 = 1 个纯色核心 + 约 30 种 AA 混色边缘 | 核心色 `(41,31,206)`，混色如 `(62,53,211)` / `(105,98,221)` |
| 每字符颜色**互不相同**（Kaptcha 特性），可据此切分 | 60 张样本全部成立 |
| **噪点是独立小团块**，不依附字形；用连通块可分离 | blob 分析：`#57` = 两段 30/28px 竖线 + 1px 孤立点 |
| **按连通块提取（≥8px）** 能稳定得到 4 个字符 | 60/60 张全部恰好 4 块 |
| 4 字符 x 槽位固定：`(0,20) (21,46) (47,73) (74,99)` | 逐列墨迹直方图 |

### 关键教训：早期提取方式是错的

第一版用「**严格颜色相等**」提取，把抗锯齿边缘像素全丢了，导致字形斜线
被削成 1px（服务器实际是 2px）。表现为「看起来结构对但逐像素差 16~25」。
**正确做法**：按连通块提取，保留核心 + AA 边缘。

同理，早期「取出现次数 ≥15 的颜色当核心色」也会把**噪点色**误判成字符色，
出现过 bbox 横跨 83px 的荒谬结果。

### 字体匹配结果：失败

生成 Java AWT 字模库（本机 Java 与服务器同为 AWT 光栅器）：

| 数据库 | 覆盖范围 | 精确命中 |
|---|---|---|
| `awtdb.txt` | 7 字体 × style0-1 × size11-34 | 0/66（旧提取） |
| `widedb.txt` | 7 字体 × style0-3 × size10-40 | 8/66 |
| `allfonts.txt` | **929 个可用字族** × style0-1 × size10-26，94 万条 | **27/240** |

`allfonts.txt` 精确命中的 27 个**全是纯横竖笔画字形**（`I` `E` `F` `L` `H` `T`），
且分散在 5 个无关字族里 —— 属于**平凡形状的巧合命中，不是真匹配**。
含斜线/曲线的字形（`N` `M` `X` `g` `8` `B`）**无一命中**，最小差 7~18px。

对照实验：样本 `X`（11×13，笔画约 4px）与 `Tahoma style1 size18`（11×13，
笔画 3px）形状明显不同 —— 样本更粗更圆。**服务器用的字体不在本机 929 个
字族之内。**

### 未走通的原因与可用的替代方案

「逐像素精确匹配」需要客户端拥有**与服务器完全相同的字体文件**。本机
字体集与服务器不同 → 此路不通。

可选方案（按推荐度）：
1. **采集带标注的样本自建模板库**：对同一字符多次采样，取「多数投票」的
   位图作模板；或用已上线的人工识别结果做标注积累。需要标注成本。
2. **特征匹配代替逐像素**：把字形归一化到固定网格，提取
   「笔画数 / 孔洞数 / 投影直方图 / 矩特征」等，用最近邻分类。**不依赖字体**，
   是 OCR 的标准做法，预期准确率足够（4 字符、字符集仅 63 个）。
3. **接入现成 OCR**：系统若已有 tesseract 可直接调用（需验证 4 字符
   小图准确率，通常需要预处理）。

### 顺带发现的真实缺陷（待修）

`crates/gnnuhub-ocr/src/lib.rs` 的 `validate_captcha_format` 用
`is_ascii_alphanumeric()` 校验，但样本 `0009.png` 实测含 `+` 号字符 ——
**该函数会拒绝合法验证码**，是个必须修的 bug。

## 第三轮：用 tesseract 做识别（用户指定）

系统 **tesseract 5.5.3**（`/usr/bin/tesseract`），有 `eng` 语言包。

### 关键结论

**（1）整图识别 > 逐字符识别。** 整图（`--psm 7`，灰度，放大 3~5 倍，
LANCZOS 插值）能利用上下文，直接输出 4 字符；逐字符（`--psm 10`）反而
更差，因为失去上下文且小图信息量不足。

多配置投票（12 种预处理 × 缩放组合）后：

| 指标 | 结果 |
|---|---|
| 有 4 字符结果 | **55/60** |
| 高置信（≥6 票一致） | 33/60 |

**（2）与已知答案吻合。** 之前独立核对过的样本，tesseract 给出了一致的
结果：`0010 → NIg8`（= 我人工核对的 `Nlg8`）、`0014 → LD60`、
`0016 → KOUa`、`0006 → P7kg`。这是强证据。

**（3）大小写是真实存在的（回答"是不是大小写"）。** 三个独立证据：

- 整图识别 220 个字符中，**大写 85（38.6%）、小写 94（42.7%）、
  数字 41（18.6%）** —— 三类的占比接近均匀，大小写都在。
- **含大写字母的图 42/60，含小写的 47/60，同一张图内混用大小写/数字的
  48/60** —— 不只是全大写或全小写，而是**逐字符随机大小写**。
- 同一字号下存在 **6~8 种不同字形**（如 8x10 有 6 种），其中包含
  大小写对（如 `u`/`U` 同为 8x10 但形状不同）。

**（4）字符集估计是 `A-Z` + `a-z` + `0-9` = 62 个字符。**
整图识别共产出 **61 个不同字符**（大写缺 `Q`，小写全、数字全）。
逐字符识别只覆盖 43 个，是因为 65 个字形样本量不够，稀有字符没采到 ——
**不是字符集小，而是样本少**。

### 为什么逐字符识别覆盖不全

65 个唯一字形来自 240 个样本位置。若字符集 62 个、均匀分布，240 次采样
平均每字符 ~3.9 次，但存在大小写多形态，实际每个"字符 × 字号"组合更稀疏。
所以 65 个字形只覆盖 43 个字符是**采样不足**的必然结果，不是识别错误。

要覆盖全字符集，需继续采样到 **600~1000 张**，才能让每个字符出现 ~10 次。

### tesseract 的可靠性问题

- 65 个字形里 **21 个（32%）在四种缩放下结果不一致**，5 个出现多字符输出
  （如 `'F4'`、`'b4'`），说明单字识别不稳。
- 常见混淆对：`I`/`1`/`l`、`O`/`0`、`Z`/`2`、`S`/`5`、`g`/`9`、`w`/`W`、
  `C`/`c`。这是 62 类（含大小写）分类下 tesseract 的固有弱点。

### 最终算法

### ⚠️ 本轮踩到的两个新坑（都已加回归测试）

**坑 1：灰度系数必须用 BT.601，不能用 `DynamicImage::to_luma8`**

| 实现 | 系数 | 分母 |
|---|---|---|
| PIL `convert("L")` | 299, 587, 114 | 1000 |
| `image` crate `to_luma8` | 2126, 7152, 722 | 10000 |

验证码每字符颜色随机且常高饱和，两者差 10~33 阶：
`0024.png` 从 `0Cax` 变 `0Gax`、`0036` 从 `hW5F` 变 `hWsF`、
`0041` 从 `9SIj` 变 `9S1j`、`0056` 从 `0iS1` 变 `0is1`。
**全部离线调参基于 PIL 灰度图，Rust 侧必须复现同一公式。**

**坑 2：PIL 是四舍五入，不是整除**

必须写成 `(R*299 + G*587 + B*114 + 500) / 1000`。漏掉 `+500` 会在
60 张样本上造成 4/60 的判定分叉。用 `np.array_equal` 逐像素验证过
`(R*299+G*587+B*114+500)//1000` 与 `convert("L")` 完全相同。

### ⚠️ 尚未解决的问题：方案对放大倍数敏感

同一张 `0024.png`，只有 **scale 4~8** 窗口内 tesseract 读出正确的
`0Cax`；scale 2/3/10 都退化成 `0ax`。即：

```
scale    2     3     4     5     6     7     8    10
psm8   0ax   0ax  0Cax  0Cax  0Cax  0Cax  0Cax  0ax
```

而且滤波器选择是刚性的：PIL 的 NEAREST/BOX/BILINEAR/HAMMING/BICUBIC
**全部**读出 `0ax`，只有 `LANCZOS` 能读出 `0Cax`。

Rust `Lanczos3` 与 PIL `LANCZOS` 在放大后仅差 3 个像素各 1 阶
（第 60 行：`[3]` 244→243、`[11]` 159→160），但足以让 `C` 变 `G`。
**这说明 tesseract 在低对比度抗锯齿边缘上处于决策边界附近，鲁棒性不足。**

改进方向（未实施）：在 scale 4/5/6/7 多个倍数上取共识，而不是只用 5。

## 第六轮：位图查表路线 — 提取器的实质 bug 与字体指纹

### 已确认的关键事实

1. **服务端字形是确定性的**：同一个 (字符, 字号) 在不同图片、不同颜色下
   渲染出**逐像素相同**的位图。证据：一个 `4x14` 位图在 7 张图里复现 8 次，
   而来源颜色各不相同（`(162,229,60)`、`(106,118,49)`、`(135,58,188)`…），
   二值化后完全一致。=> 位图查表是可行的，上限只取决于库覆盖度。

2. **库空间约 67 个位图，已采样 65 个**（Chao1: S_obs=65, u1=8, u2=13）。
   采样覆盖度 96.7%，估计仅剩约 2 个未发现。60 张样本基本已榨干库空间。
   识别率随库大小：10 张→45.2%、30→82.8%、55→**96.7%**。

3. **验证码字符集 = 数字 + 小写 + 大写**（61 个不同字符被观察到），
   这回答了之前「大小写是不是只有一种」的疑问 —— **大小写是区分开的**。
   大小写由**字形高度**承载：cap-height 顶 `y0=5`（h≈13），
   x-height 顶 `y0=8`（h≈10），ascender `y0=4`（h≈14）。

### 提取器的实质 bug（已修）

`.scratch/extract2.py` 用 `len(blob) >= 8` 过滤"噪点"，把 **i/j 的点**当成
噪点扔掉了：全样本共 13 个 `2x2`/4 像素的孤立小块，全部是 i/j 的点，
**没有任何真正的随机噪点**。

后果：同一个 `i`（有点）和 `l`（无点）在有点情形下被截成无点主干，
于是 `i` 与 `l` 的位图混在一起无法区分。

修正：`.scratch/extract4.py` 把「宽<=3 且高<=4 且像素<=8」的小块按
x 区间重叠 + 位于主干上方(间距>0) 的规则合并回主干。

修正后 `2x14` 从 5 个涨到 10 个，并新出现 8 个 `4x18` —— 后者与
DejaVu Sans size18 的 `j` 合成渲染**几乎逐像素一致**（仅尾部差 1 像素）。

**教训：噪声过滤阈值必须验证，不能想当然。** 这批验证码其实没有噪点。

### 字体指纹

用 42 个高置信字形的 (w,h) 尺寸向量去匹配合成字体库
（`.scratch/awt/wide2.txt`，37076 条，7+ 字体 × 2 样式 × 字号 10~32）：

```
DejaVu Sans  style=0  size=18  ->  39/42 命中  ← 服务端字体
Verdana      style=0  size=18  ->  25/42
Tahoma       style=0  size=18  ->  20/42
```

**服务端用 DejaVu Sans（无衬线）常规体，字号约 18，开启抗锯齿。**

但注意：**合成库（关抗锯齿直接栅格化）与真实字形（抗锯齿后二值化）
逐像素不相等**，65 个真实字形对合成库的精确命中数为 **0**。
所以不能拿合成库当查询表，只能用来判定「字体身份」和「几何关系」。

### I / l / i / j 的本质歧义

DejaVu Sans 下 `I` 与 `l` 的主干**逐像素完全相同**（size18 都是 `2x13` 实心条），
`i` 的点与主干之间有空行、`j` 有降部勾。因此：
- 有点 + 底 18 -> `i`；有点 + 底 22 -> `j`（可由提取器判定）
- 无点 -> `I` 与 `l` **在位图层面不可区分**，必须靠上下文/先验

这不是标注错误，是信息论层面的上限。

### tesseract 在两源分歧上的表现

单字符模式（psm10，21 配置 × 每次出现，20~100 票/位图）系统性**偏向大写**；
整图模式（psm8/13，看得到基线）大小写更可靠。两者冲突 22 例中，
绝大多数是**纯大小写分歧**（`Z`/`z`、`J`/`j`、`U`/`u`、`W`/`w`…），
而 4x18 那条 `j` 的合成比对证明**小写确实是独立字形**，不是读数噪声。

=> 大小写裁决应以**整图模式**为准，并以**字形高度**做独立佐证。
