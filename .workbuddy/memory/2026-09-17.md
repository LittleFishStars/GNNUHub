## 真实账号登录实测（commit f1b8511）

**凭据**：学号 250710078（用户授权测试）

### 实测 SSO 完整链路（重要，与 Python 版认知不同）

```
GET /sso/lyiotlogin?ticket=ST-xxx
  → 302 /sso/lyiotlogin            种下 /sso 下的 JSESSIONID
GET /sso/lyiotlogin
  → 302 /ticketlogin?uid=...&verify=...
GET /ticketlogin?...
  → 302 /xtgl/login_slogin.html    ⚠️ 这是中转，不是失败终点
GET /xtgl/login_slogin.html
  → 302 /xtgl/index_initMenu.html  会话成立
```

**关键结论**：`login_slogin.html` 路径名像登录页，但持有有效 ticket 时
它只是中转站，**必须继续跟随**。判断会话成立看是否落在 `index_initMenu`
或遇到非 3xx。若跳回 `cas.gnnu.edu.cn` 说明 ticket 失效。

### 真实接口响应与 Python 版推导的差异

1. **`meta.success` 不可信**：实测出现 `meta.success=true` 但
   `data.code="CODEFALSE"`（验证码错误）的响应。只信 `meta.success`
   会把验证码失败误判成登录成功。已改为优先判据 `data.code`。
2. **`statusCode` 是整型**：线上返回 `"statusCode": 200`（int），
   不是字符串。原代码按 String 反序列化会报
   `invalid type: integer 200, expected a string`。
   已改为 `serde_json::Value` 并做归一化。
3. 验证码 **uid 单次有效**，同一 uid 提交两次返回 CODEFALSE。

### 网络环境陷阱（踩坑记录）

- **本机有 `https_proxy=http://127.0.0.1:39429`**，`curl` 会走它，
  但 `reqwest` 在 `default-features=false` 且未启用 `system-proxy`
  时**不会**读取该环境变量。两边行为不一致，排查时容易误判。
- **DNS 只返回 IPv6**（`2001:250:...`），本机**无 IPv6 默认路由**。
  curl 有 Happy-Eyeballs 回退，reqwest/rustls 没有。不过实测 reqwest
  在 A 记录存在时能正常回退到 IPv4，此项不是主因。
- **`cas_headers()` 的 `Host` 覆盖是双刃剑**：CAS 反向代理只认
  `Host: cas.gnnu.edu.cn`，所以必须覆盖；但若把这个 HeaderMap 复用到
  教务系统域名，会因 Host 与 SNI 不匹配被服务端直接关连接
  （`peer closed connection without sending TLS close_notify`）。
  已拆出 `cas_headers_for(host)` 并加测试锁死约束。
- 教务系统网关带 **SafeDog WAF**（会种 `SF_cookie_17`）。
  短时间高频探测后，jwgl 与 cas **两个域名同时**在 ~70ms 内拒绝连接，
  而外网正常 → 属于按 IP 的临时封禁，需等待解封。

## 会话交换根因定位（commit 112ce03）

### 真正的根因：跟多了，不是跟少了

**此前判断有误**。之前以为是 WAF 限流导致第 4 跳失败，实际是
**实现本身多走了一跳**。对照 Python 版 `api.py` 的 `Student.__init__`
后确认正确流程：

```
① GET /sso/lyiotlogin?ticket=ST-xxx
     → 302 /sso/lyiotlogin          种下 /sso 作用域的 JSESSIONID
② GET /sso/lyiotlogin        （带 ① 的 Cookie + CASTGC）
     → 302 /ticketlogin?uid=...&verify=...
③ GET /ticketlogin?...
     → 302 /xtgl/index_initMenu.html   种下 / 作用域的 JSESSIONID
```

**在 ③ 收到 3xx 后必须立即停止。** 之前会继续跟到
`/xtgl/login_slogin.html`，而服务端把「已持有会话却重放登录页」
判定为异常，直接关闭 TLS 连接。这就是稳定复现的
`peer closed connection without sending TLS close_notify` 的真正原因——
它与请求频率无关（加了节流后依然失败），是行为层面的拦截。

**教训**：路径名叫 `login_slogin.html` 不代表它是链路终点；
反过来，也不是「跟得越全越保险」。应严格对照已验证的参考实现。

### Cookie 作用域坑

`/sso` 与 `/` 下会各有一个同名 `JSESSIONID`，**必须丢掉 `/sso` 那份**。
原实现「后出现的为准」恰好会选中错误的一份。
Python 用 `self._cookie.clear('jwgl.gnnu.edu.cn', '/sso', 'JSESSIONID')` 显式清理。
Rust 版改为解析 `Set-Cookie` 的 `Path` 属性，新增 `is_sso_scoped()` 分离，
`exchange_ticket_for_session` 内用 `sso_jsessionid` 变量暂存待丢弃的值。

### 已加入的防御

- `ClientConfig::request_interval`（默认 600ms），所有请求走 `Client::throttled`。
- 重试间隔由 400ms 增至 1200ms（需大于节流窗口才有意义）。
- `hop_limit` 由 `max(10)` 收紧为 `max(5)`（实际只需 3 跳）。
- `Session::new` 提升为 `pub`，支持从持久化 Cookie 恢复会话。

### 封禁行为实测

`gnnu.edu.cn` 全域名（含 `www`）在触发风控后，于 ~70ms 内拒绝连接，
而其他站点正常。**同一 block 内两次触发**：上次是探测量大导致，
这次是加了节流后仍因「重放登录页」触发——说明该校的风控不只按频率，
也按请求行为模式。**待办：解封后复测**（代码已修正，预期可通）。
